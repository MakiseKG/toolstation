Base64 是开发者几乎每天都会遇到的编码方式，但很多人只用却不懂它。这篇文章将带你深入理解 Base64 的原理、应用场景，以及最常见的几个误区。

## Base64 是什么？

Base64 是一种用 **64 个可打印字符** 来表示任意二进制数据（字节流）的编码方式。它解决了「二进制数据无法直接放进文本协议」的问题。

这 64 个字符是：

- 大写字母 A-Z（26 个）
- 小写字母 a-z（26 个）
- 数字 0-9（10 个）
- `+` 和 `/`（2 个）
- 再加上 `=` 作为填充字符

## 原理：3 个字节 → 4 个字符

Base64 的核心规则很简单：**每 3 个字节（24 位）分成 4 组，每组 6 位，再映射成对应的字符**。

```
原始数据:    01100001  01100010  01100011   (abc)
6位分组:     011000   010110   001001   100011
映射字符:    Y        W        J        j
结果:        YWJj
```

当字节数不是 3 的倍数时，末尾会用 `=` 填充，使总长度始终是 4 的倍数。

## 应用场景

### 1. 图片内嵌到 HTML / CSS（Data URI）

这是前端最常用的场景。把一个小图标转成 Base64 字符串后，可以直接写进 HTML：

```html
<img src="data:image/png;base64,iVBORw0KGgoAAAANSUhEUg..." />
```

或者作为 CSS 背景：

```css
.icon {
  background-image: url("data:image/svg+xml;base64,PHN2ZyB4bWxucz0i...");
}
```

好处是**减少 HTTP 请求**，对小图标（小于 10KB）能显著提升加载速度。用 [图片转 Base64 工具](/tools/image-to-base64) 可以一键生成。

### 2. 邮件附件

电子邮件协议（SMTP）只能传输纯文本。附件（图片、PDF 等二进制文件）会被编码成 Base64 后发送，接收端再解码还原。

### 3. API 认证

许多 API 使用 `Basic Auth`，格式是 `用户名:密码` 做 Base64 编码后放入 `Authorization` 请求头：

```
Authorization: Basic dXNlcm5hbWU6cGFzc3dvcmQ=
```

### 4. 在 JSON / XML 中传输二进制

当接口需要在 JSON 字段里传递文件内容时，无法直接塞入二进制，Base64 是最常见的选择。

## 常见误区

### ❌ 「Base64 就是加密」

**这是最常见的误解。** Base64 只是编码，不是加密：

- 编码不需要任何密钥
- 任何人都能解码还原原文
- 它完全无法保护敏感数据

需要保护数据时，请使用 AES 等真正的加密算法。Base64 的唯一作用是「格式转换」，让二进制能放进文本协议。

### ❌ 「Base64 能减小文件体积」

**恰恰相反。** Base64 编码后体积会比原始数据大约 **33%**（因为 3 字节变成 4 字符）。它换来的是「可传输性」，而不是体积优势。

## 解码时要注意什么

用 [Base64 解码工具](/tools/base64) 时，如果解码结果出现乱码，通常是以下原因：

- 输入的 Base64 字符串有换行或空格（Base64 有时会被折行）
- 字符串末尾缺失 `=` 填充符
- 输入的根本不是 Base64，而是普通文本

## 总结

- Base64 用 64 个字符表示任意二进制数据，3 字节 → 4 字符
- 主要用途：图片内嵌、邮件附件、API 认证、JSON 传二进制
- **不是加密**，不提供任何安全性
- 编码后体积增加约 33%
